## 1. 构建与运行（快速参考）

```bat
rem 编译核心模块（最快反馈）—— 用仓库自带的 gradle wrapper
gradlew.bat :core:compileJava --console=plain
```

- **环境**：本机 Java 23（系统 PATH 里的 `java`）。本仓库**自带 gradle wrapper**（`gradlew.bat`，Gradle **8.11.1**，走腾讯镜像）。
  **不需要**任何 `D:\PD\...` 路径 —— 那套工具链属于另一个项目，本仓库没有。
- **Android SDK**：`local.properties` 的 `sdk.dir` 指向 `C:\Users\1372722790\AppData\Local\Android\Sdk`。
- **退出码 1 但输出 `BUILD SUCCESSFUL` = 正常**（javac 的 stderr 警告）。真正的失败会输出 `错误:` / `error:` 行。
- ⚠️ **沙箱下 wrapper 可能报锁文件「拒绝访问」**（`.gradle\wrapper\dists\...\*.zip.lck`）：那是文件沙箱限制，
  **不是配置错误**；编译任务默认交由用户自行执行。
- **AI 代理工作流**：编译成功后**不要自行启动游戏**——游戏窗口无输出可采集，游戏内内容只能人工验证；直接告知用户进行测试即可。
- **Android APK**：`gradlew.bat :android:assembleDebug` → 产物
  `android\build\outputs\apk\debug\android-debug.apk`（debug 签名，可直接安装；`assembleRelease` 未配置签名）。
  - **版本号**：根 `build.gradle` 的 `ext.appVersionCode / appVersionName`。编码约定 **`900 + minor*10 + patch`**
    （0.2.5⇒925、0.3.0⇒930）；打包后 `output-metadata.json` 与 `aapt dump badging` 均可核对实际写入值
    （debug 变体 `versionName` 加 `-INDEV` 后缀、`applicationId` 加 `.indev` 后缀）。
  - **打包前先确认没有别的构建在跑**：桌面调试（`:desktop:debug`）会长时间持有
    `.gradle\...\executionHistory\executionHistory.lock`，此时其它构建一律以 `executionHistory.lock (拒绝访问。)` 失败
    （哪怕加了 `--no-daemon`）。正确做法是等游戏退出/桌面构建结束再打包；
    **不要**用 `--project-cache-dir` 另开缓存来绕锁 —— 两个构建会互踩 `android\build\intermediates`，表现为 dexBuilder 写
    `desugar_graph\...\graph.bin (拒绝访问。)`。
- 只改文本（messages 属性文件）时无需动代码，重新打包即生效。

## 2. 文本与本地化

- **大多数文本**在 `core/src/main/assets/messages/*_zh.properties`（`actors` 怪物/buff/天赋/技能、`items` 物品、`windows` 窗口、`journal` 日志、`levels` 楼层、`misc` 杂项）。格式：`键=值`；`_xxx_` 强调色；`\n` 换行；`%s`/`%1$d` 是占位符**不可删**。
- **行内标记**：`_文字_` / `**文字**` = 强调色，`~~文字~~` = 删除线（画上去的，字体没有组合删除线字形）。细节：`GLog` 的 `~~ ` 前缀不会与正文串味。
- **自定义职业/物品常大量使用硬编码中文**（不走 messages），改文本需改代码，硬编码文本要在源码里搜。
- `Messages.get(Class, key)` 会沿**父类链**查找键：子类未定义 `desc` 等键时继承父类文本（新武器复制短剑文本即靠此机制）。
- **「列表类」技能文本必须自带技能名**：统一走 `ArmorAbility.namedShortDesc()`（描述已含名字就原样返回，否则开头补一行 `_技能名_`）。三个消费点已全部改用它。
- 上述列表用的是 `RedButton`（`StyledButton`）+ `RenderedTextBlock`，两者都支持 `\n` 硬换行与 `_强调_`；`WndChooseAbility` 的按钮高度靠「先 `setSize` 触发一次布局 → 再 `reqHeight()` 取换行后真实高度」这套写法（同 `WndMonkAbilities`），所以**给按钮文字加换行不会溢出**。
- **数值类信息只写在「描述文本」里，`GLog` 不写具体数字**（用户约定）：门槛/消耗/百分比写进 `desc`，即时报文只给感受性措辞（顺带避开格式化坑）。
- **改一个机制的「行为」时，先 `grep` 全部提及它的描述键**：同一套机制通常在 3~4 个键里各写了一遍（招式 `desc` ×2 语言 + 天赋 `desc` ×2 + 职业长描述）。改之前先全部搜出来一起改。
- **描述文本只做功能描述，不写修饰句**（用户约定）：`desc` 直接从 `_+1：_` 或效果本身起笔；**层级标签首档也要带下划线**；zh/en 必须同步（英文侧最常漏改）。
- **换行只认反斜杠 `n`**：`\n\n` 误写成 `/n/n`（正斜杠）**不会换行也不报错**，只会在面板里原样显示 `:/n/n_+1:_`。批量核验：`grep -c "/n/" core/src/main/assets/messages/ -r` 应为 0（2026-09-16 在 `actors.properties` 一次揪出 9 处，全在手掌/前二老板的 T3 天赋里）。
- **用脚本批量写 `*.properties` 时，落盘前必须把真换行转成字面量 `\n`**：否则一条 entry 断成多行、续行没有 `=` ⇒ 被解析成一堆垃圾键，而**加载不报任何错**。落盘后必须回读校验 entry 条数与行尾。

## 3. 贴图与图标

- **items.png 现为 256×800（50 行）**（2026-09-12 由 640 扩到 800，行 41-50 为最新扩展预留区，除 41行1列外空白；行 36-40 为自定义内容区：36行1/2=割腕/悔恨、37-40行=人体派作品武器图标，**39行7/8列=泪锋的加护两形态**，其余空白）：`ItemSpriteSheet.TX_HEIGHT` 必须等于实际高度，否则全物品图标错位（曾因 528→544、576→640、640→800 未及时同步而出过全局错乱）。PNG 高度可从 IHDR 读取（**大端**，PowerShell 读 Int32 需反转字节，宽=偏移16-19、高=偏移20-23）。
- `xy(列, 行)` 是 **1 基**（**第一参=列、第二参=行**，内部 `x-=1; y-=1`），每行 16 格（WIDTH=16）。例：GLOWING_PEBBLE=xy(8, 32) 即"32行第8个"。
- 非 16×16 图标用 `assignItemRect(常量, 宽, 高)`；超大贴图（如薄暝 20×20、失乐园 21×20）会超出格子，是预期测试内容。
- **职业护甲图标占 items.png 第 12 行**：`private static final int ARMOR = xy(1,12)`（16 格），依次 `ARMOR+0..+4` 五套普通护甲、`+5..+10` 六职业护甲、`+11` 食指西服（神谕）、`+12` 环指长袍、`+13` 拇指大衣（VALENCINA）、`+14` **中指外套（MIDDLE_FINGER，`xy(15,12)` 16×16）**。新增时：常量声明要写在下面那个 `static{}` 赋值块**之前**（静态初始化按源码顺序执行），并在块内补 `assignItemRect`。
- **自定义职业天赋图标**：为自定义职业新增天赋时，图标一律写在 talent_icons.png 对应预留行，枚举值直接写**绝对索引**并烘焙进枚举，`icon()` 内按 `case <职业>` 特判返回该索引；**禁止**按当前职业对所有天赋做全局行偏移（旧写法 `+7*32` 已废弃）——会让其他职业天赋（枚举图标 ≥64）索引越界 → `TextureFilm.get` 返 null → NPE，蜕变卷轴替换窗口必现闪退。索引位置必须与图内实际绘制一致（历史上出现过两次"整体差 1 格"错位）。各职业各占一行（神谕=第八行、环指=第九行）。
- 英雄/技能图标：`ui/HeroIcon.java`（hero_icons.png 帧号）；buff 图标：`ui/BuffIndicator.java`（连续编号）。新图标需先画进贴图再引用，否则显示空/错位。分配新图标索引前，先在 `ui/HeroIcon.java`、`ui/BuffIndicator.java` 里查已占用值。
- **动画贴图复用**：`index.png` 与 `guard.png` 同规格（256×16、12×16 帧）时直接照抄 `GuardSprite` 换 `Assets.Sprites.INDEX` 即可。
- **英雄皮肤帧尺寸**：原版 7 职业 256×128、帧 12×15、21 列 × 8 行；`RING_MASTER` 用 `callisto.png` 20×24 帧独立缓存。**自定义职业只要保持 256×128 / 帧 12×15 / 21×8 就直接复用 ROGUE 的 film，一行代码都不用改。**注意变化点：tier 行分配、`frameSize()`、两处直接切片消费者、存档槽 12×15 截取；第 7 行之后要另建 film。
- **音效 / 音乐**：真源都在 `core/src/main/assets/`（Android 直读；桌面 `processResources` 倒进 jar 根）。**新增音效三步**：① mp3 进 `sounds/`；② `Assets.Sounds` 加常量**并加进同类 `all[]` 数组**（漏第②步**静默无声**）；③ 触发点 `Sample.INSTANCE.play(...)`。注意音量与加载时机（改了音频资源要一起核对）。


- **地图贴图（分层 tilemap / 跨格拼帧 / 草皮遮挡）**：动地形/图集/草皮/遮挡时先在 `core/src/main/java` 里 `grep` 现有地形实现。
- **用户新放素材的正确查法（2026-10-24 血泪教训：中文文件名会被 PowerShell 显示成乱码而误判"文件不存在"）**：
  用户说"我放好了"时，**禁止**用 `Get-ChildItem | Format-Table Name` 的默认输出判断有无文件（中文名会变成 `��.png` 之类）。
  一律改用下面这段（UTF-8 控制台 + .NET 直接取路径，中文完整可读，并按时间倒序看最新）：
  ```powershell
  chcp 65001 > $null
  [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
  $d = "<目标目录>"
  $files = [System.IO.Directory]::GetFiles($d)
  for ($i=0; $i -lt $files.Count; $i++) {
    $fi = New-Object System.IO.FileInfo($files[$i])
    "{0} | {1,8} KB | {2} | {3}" -f $i, [math]::Round($fi.Length/1KB,1), $fi.LastWriteTime.ToString('MM-dd HH:mm:ss'), $fi
  }
  ```
  要点：① 先 `chcp 65001` 且设 `[Console]::OutputEncoding`；② 用 `[System.IO.Directory]::GetFiles` 而非 `Get-ChildItem` 的管道输出；
  ③ **按 `LastWriteTime` 倒序看最新几条**，用户强调"看时间"时尤其如此；④ 中文名文件用 `read` 工具按**完整中文路径**读取，不要用列表里看到的乱码名去猜。
  ⑤ 若目录里确有中文名文件但读图仍失败，先 `Test-Path` 完整中文路径确认真实存在，再 `read`。
- **APK 桌面图标 / 应用名**。三条最容易踩的：
  1. **一张 `ic_launcher.png` 决定不了任何事**：`AndroidManifest` 的 `android:icon="@mipmap/ic_launcher"` 在 **API 26+ 只解析 `res/mipmap-anydpi-v26/ic_launcher.xml`**（自适应图标 → `_background` + `_foreground` + `_monochrome` 三张分图层），`res/mipmap-*/ic_launcher.png` 那套扁平图**只在 API < 26 才被读**。铁证：`aapt dump badging` 打出来的 `application-icon-120/160/240/320/480/640` **六档全部指向同一个 `mipmap-anydpi-v26/ic_launcher.xml`**。⇒ 只重画扁平图＝真机零变化（2026-09-18 实测踩中）。
  2. **`android/src/debug/res/` 是 `main` 的整套副本且会覆盖 main** ⇒ 图标改动必须 **main + debug 各一遍**（4 种 × 5 档 × 2 套，另加两个 ldpi 扁平图）。
  3. **改「显示名」安全，改「应用身份」是灾难**：桌面名来自根 `build.gradle` 的 `appName`（→ `manifestPlaceholders` → `android:label="${appName}"`）；而 Android 存档按 **`applicationId`** 定位（`getFilesDir()`＝`/data/data/<pkg>/files/`，偏好文件名还是硬编码的 `"ShatteredPixelDungeon"`）⇒ 改 `appName` **不影响移动端存档**，改 `appPackageName` 等于换一个 App、老存档全成孤儿。另注意 debug 变体带 `applicationIdSuffix ".indev"` ⇒ debug/release 是**两个独立 App、两套独立存档**，别误判成丢档。**桌面端例外**：`DesktopLauncher` 的数据目录原本拼的是 `%APPDATA%\.mypd\<title>\`、而 `title` 就是 `appName` ⇒ 改名会让桌面老存档变孤儿；已把目录名冻结成独立的 `saveDir` 常量（与显示名解耦，改产品名不再动存档路径）。
  - **改图标后必须实测**：读 PNG 的 IHDR 确认尺寸、逐像素 diff 确认颜色真的换上了（本仓库无现成工具，脚本自己写）。

## 11. 版本控制 / 提交与 PR 规范（红线 · 必守）

> 追加于 2026-10-11。**每个新功能必须照此执行**，禁止“少量提交堆大量改动”。

- **一功能一分支**：开始任何新功能/独立改动前先切分支：`feat/<短名>`、`fix/<短名>`、`refactor/<短名>`、`docs/<短名>`。禁止在主干或一个分支里混做多个不相干功能。
- **一独立改动一提交**：把工作拆成“可独立说明”的小步，每步单独提交。**禁止**把多个不相关改动塞进一个提交。
- **提交信息遵循 Conventional Commits**：`<type>(<scope>): <description>`；type 用 `feat|fix|refactor|perf|docs|style|test|chore|build|ci`；description 用祈使句、简短，说清“改了什么”；必要时在正文写“为什么/怎么做”。
  - 例：`feat(artifact): add Shadow Dancer third subclass`
  - 例：`fix(druid): pass real damage to subclass onAttackProc`
  - **`type` 语义（2026-10-11 澄清）**：`docs` **只**用于 `docs/` 下的**开发参考文档**；**游戏内文本**（`core/src/main/assets/messages/**/*.properties`、以及硬编码的物品/怪物/界面文案）属于本地化内容，用 `fix(i18n): ...` / `feat(i18n): ...`（scope 也可写 `description` / `text`），**不要用 `docs`**。分支名同理，文本改动用 `fix/<短名>` 而非 `docs/<短名>`。
- **一功能一 PR**：PR 描述写**新功能说明**，或**改已有内容时的思路与做法**（背景→做法→影响→回滚）。禁止一个 PR 里堆上百文件却只有几笔提交。
- **开工前先 `git status` / `git branch`**；确认当前分支与改动范围；提交前逐条 `git diff --stat` 复核，确保提交内容单一。
- **本地提交后自动推送当前独立功能分支**（`git push origin <branch>`；网络不稳时带 §0.0 的代理参数）；**不擅自合并、不动 `main`、不擅自开 PR**。
- 文档：任何 `.md` 改动也单独一个 `docs(...)` 提交。
- **自动提交（2026-10-12 起，用户明示）**：每完成一个「独立、可说明」的改动就**自动 `git commit`**（严格遵循上面的 Conventional Commits 格式与 type 语义），**无需用户每次提醒**；**提交后自动推送当前独立功能分支**（2026-10-22 用户明示），**仍不擅自合并、不动 `main`、不擅自开 PR**。
- **提交信息语言＝中文（2026-10-12 起，用户明示）**：`<type>(<scope>): <中文描述>` —— `type`/`scope` 保留英文约定（`feat`/`fix`/`refactor`/`docs`/`i18n`…），**冒号后的描述一律用中文**、祈使句、简短。例：`fix(alchemy): 修复药剂蒸馏回调越界闪退`。
- **本地打包＝测试版，但提交必须保留 Firebase（2026-10-22 用户澄清）**：打包成 APK 时可以**临时**移除/绕过 Firebase（`AndroidLauncher` 的 `initializeApp`、manifest 两个 provider）以保证能启动；但**提交前必须恢复**这些代码与 google-services/crashlytics 插件/依赖，否则会丢失数据统计功能。判断依据：**提交里绝不能包含这些临时移除**；本地测试包不受此限。

## 12. 改动边界与最小侵入原则（红线 · 必守）

> 追加于 2026-10-24（用户明示）。起因：为「哥布林骑手」给 sprite 加了 `perspectiveRaise` 补偿，把原本正常的精灵顶得与相邻格重叠；又为让它好测，改了 `Dungeon.init()` 和生成逻辑。**改一处坏一处，排查成本远超收益。**

### 12.1 只碰「新东西」本身，不动既有机制

- 新增怪物 / 道具 / 技能 / 分支时，**改动范围必须收在新增文件 + 必须注册的那一行**（`Assets.java`、`Branches.java`、`Generator` 等）。**不要**顺手改 `CharSprite`、`Mob`、`Level`、`Dungeon` 等公共基类去「适配」新东西。
- 新东西表现不对时，**先怀疑是新增代码写错了**，而不是既有框架不兼容。标准单位（16×16 精灵、常规怪物）能正常显示，说明框架没问题 —— 问题一定在新代码里。
- 需要「调参」时（位置、高度、速度、伤害），**用新增类里的局部常量或方法参数**，不要在基类里改全局默认值。

### 12.2 明确禁止：为测试便利改动游戏逻辑

- **禁止**为了让新内容好测试而修改 `Dungeon.init()`、`createMobs()`、`InterlevelScene`、存档结构等。测试要走**既有正路**（正常探索、测试模式道具、已有传送器）。
- 如确需临时调试代码：**必须**加 `//[TEMP-DEBUG]` 标记，**同一次会话内删除**，并在提交前 `grep TEMP-DEBUG` 复核为 0 命中。
- 验证时必须**实际跑起来看**，不能只靠读代码或 `git log` 下结论（教训：曾用 `git log` 核对文本「内容一致」就判定没问题，实际是 properties **键名**写错，游戏一直显示占位符）。

### 12.3 精灵尺寸不匹配时的正确做法

- 标准精灵是 **16×16**。若素材是 16×18 等非标准尺寸，**优先把素材裁/缩回 16×16**（去掉多余透明行），而不是改 `perspectiveRaise` 等渲染参数。
- 只有当素材**确实无法**压到 16×16（如 DM300 的 25×22、Yog 的大体型）才参考对应类的做法，且**必须在注释里写明为什么这里要特殊处理**。
- 判定「要不要补偿」的依据：**同目录/同类怪物的 sprite 有没有写**。大家都没写，你也不写。

### 12.4 本地化键名必须带包路径

- `Messages.get(obj, "key")` 的键 = **完整类名去掉 `com.shatteredpixel.shatteredpixeldungeon.` 前缀** + `.` + key。
- 例：`actors.mobs.RadishEnemy.GoblinRider` → `actors.mobs.radishenemy.goblinrider.name`（**全小写，且保留 `radishenemy` 这一层**）。
- 新增怪物/物品后，**必须**核对现有同类条目的键名格式，不能照感觉写。
- 症状识别：游戏里显示的是**类名**或**原始 key**，而不是中文 → 键名不对，不是文字没写。

### 12.5 改完自检清单

1. `git diff` 里除了新增文件，**只应有「必须的注册行」**；
2. `grep TEMP-DEBUG` == 0；
3. 本地跑一遍，**亲眼看到**目标表现正确；
4. 若改动波及公共类，必须说明「为什么非改不可」并评估对所有其他内容的连带影响。


## 13. 新内容的测试入口与出包清理（红线 · 必守）

> 追加于 2026-10-24（用户明示）。

### 13.1 新内容必须有「开局即可见」的测试通道

做完一个新怪物 / 新道具 / 新机制后，**必须在测试构建里让它开局就能直接看到 / 拿到**，否则验收成本极高（曾为了找一个哥布林骑手在苔藓洞穴里转了半小时）。

做法（按优先级）：

1. **首选：走测试模式**（挑战里的「测试时间」）。测试模式下 `HeroDefinition.doChallengeSpawn()` 会把 `TestBag` 与各类 `TestItem`（`FloorTester`、`MobPlacer`、`LevelTeleporter` 等）塞进背包，用它们直接跳层 / 生成怪物。
2. **次选：加一个临时开局钩子**，形如：

   ```java
   //[TEMP-DEBUG] 新内容测试入口，出包前必须删除
   ```

   典型位置：`Dungeon.init()` 末尾（改起始层/分支）、目标层的 `createMobs()`（把新怪生成在入口附近）。
3. **禁止**把测试入口写进正式逻辑分支里靠条件判断长期保留 —— 要么是独立 `//[TEMP-DEBUG]` 块，要么别写。

### 13.2 用户说「打包」时必须先清空测试入口

- 出包 **= 正常运行的游戏**，**绝不允许**带着「开局就去苔藓洞穴」「新怪刷在入口」这类测试改动。
- 打包前**逐项核对**：

  ```bat
  findstr /S /I /C:"TEMP-DEBUG" core\src\main\java\*.java
  ```

  必须 0 命中；再 `git diff` 确认没有残留的测试性改动。
- 清理后要**重新编译**再打包，不能拿带测试代码的旧产物改名。

### 13.3 出包前自检清单（与 §12.5 合并使用）

1. `TEMP-DEBUG` 0 命中；
2. 起始层/分支恢复为正常（主线 1 层）；
3. 新内容的生成逻辑恢复为「按正常规则随机出现」，不是固定在入口；
4. Firebase 三处临时移除已还原（见 §11）；
5. `git status` 干净或只剩本次功能改动。
